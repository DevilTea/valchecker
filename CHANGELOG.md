# Changelog

All notable changes to Valchecker are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and published versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **Breaking:** `isEmoji()` accepts every structurally valid emoji sequence instead of only Unicode's RGI set. The accepted set is now the UTS #51 emoji sequence grammar — an emoji-presentation character, an emoji character followed by VS16, a keycap sequence, a skin-tone modifier sequence, a regional indicator pair, a tag sequence, and a ZWJ chain of those — built from Unicode property escapes, so it still tracks the engine's Unicode version rather than a release date. Loosening a validator is breaking: inputs that used to fail now pass. Named examples, with the previous behaviour in brackets: `👍‍👍` (U+1F44D ZWJ U+1F44D) and `😀‍🚀` (U+1F600 ZWJ U+1F680), well-formed ZWJ chains that Unicode does not register; `1️` (U+0031 U+FE0F), an emoji presentation sequence that is not the keycap sequence `1️⃣`; `🇦🇦` (U+1F1E6 U+1F1E6), a regional indicator pair that is not a country; `⌚️` (U+231A U+FE0F), a redundant VS16 on a character that already presents as emoji; `🏴󠁵󠁳󠁣󠁡󠁿`, a well-formed tag sequence for an unregistered subdivision; and `👪🏻`, a modifier base and skin tone whose combination is not registered. `isEmoji({ registered: true })` restores the registered set. What stays rejected is unchanged: `1`, `123`, `#`, `*`, a lone ZWJ, a lone VS16, a lone tag character, a lone combining keycap, `❤`, `☺`, or `©` without VS16, and a component followed by VS16 — `🏽️` (U+1F3FD U+FE0F) and `🇦️` (U+1F1E6 U+FE0F) — because ED-9a admits only the presentation sequences in `emoji-variation-sequences.txt`, whose only `Emoji_Component` members are the twelve keycap bases.
- The default accepted set costs 51 ns on a bare `👍` where `\p{RGI_Emoji}` cost 5,261 ns, and 87 ns on the invalid `👍a` where it cost 5,729 ns (2026-07-28, interleaved, median of nine runs of 200,000 after a 100,000 warmup, through the built package). The gap is the property-of-strings matcher enumerating every longer registered sequence a bare base emoji is a prefix of, so it depends on how specific the input is: 104× on a bare `👍`, 43× on `🇹🇼`, and 1.3× on `👨‍👩‍👧‍👦`, which matches one alternative and stops. Both accepted sets are linear on a long valid prefix that fails at its last character, which an anchored `^(?:\p{RGI_Emoji})+$` is not — that form measures 1.485 ms against the grammar's 0.057 ms at 256 ZWJ families, and the assertion in the step's tests grows the input 64× under a 2×-linear bound so it rejects an n^1.5 regression.
- **Breaking:** the `isEmoji:expected_emoji` payload gained a `registered` boolean recording which accepted set was asked for, so a message handler can say which one rejected the value.
- The tree-shaking gate no longer sets `tryCatchDeoptimization: false`. Rollup's default is `true`, which abandons analysis of a `try` block and therefore retains a module-scope `try`/`catch` that a downstream Vite or Rollup consumer never reaches; with the option disabled the gate could not see that class of retention at all, and it missed `isEmoji`'s capability probe. All 34 scenarios are byte-identical under the default, so the gate now measures what consumers get at no cost to the reported numbers.
- `string-format/emoji-registered-valid` and `string-format/emoji-registered-invalid` measure the opt-in accepted set beside the existing `string-format/emoji-*` pair, both `compatible-subset`. `isEmoji` is the only validator with two scenario pairs, because it is the only one with two accepted sets; the competitor schema is identical in both pairs, since neither Zod pin nor Valibot has a registered-set mode. The full tier is 241 scenarios and 1,104 cells, the standard tier 170.

- Every built-in step directory is now authored to one standard, written down in `.claude/skills/valchecker-dev/references/step-unit.md` and enforced by `pnpm steps:complete`: the required files are `<name>.ts`, `<name>.test.ts`, `<name>.bench.ts` and a one-line `index.ts`; the only auxiliary test is `<name>.types.test.ts`, whose assertions `pnpm typecheck` rather than vitest decides; a helper module is kebab-case after the concept it owns; and `<name>.ts` runs imports, contract types, `type Meta`, `interface PluginDef`, module-private values, then the `implStepPlugin` export as its last statement. Applied to all 114 steps with no behaviour change: fifteen auxiliary test files (`collectAllIssues.test.ts` in seven directories, `lazy-output.test.ts`, `native-snapshot.test.ts`, `check.narrow.test.ts`, `map.async.test.ts`, `strictObject.async-missing.test.ts`, and three `intersection.*.test.ts`) folded into their step's suite as further `describe` blocks, each keeping the `createValchecker` instance it was written against — the sorted multiset of `it`, `test` and `describe` title lines under `packages/internal/src/steps` is identical before and after, so no case was added, removed, renamed or merged; twenty-two implementation files had their module-private values moved below `PluginDef`; and `isAtLeast`, `isAtMost`, `isLengthAtLeast` and `isLengthAtMost` dropped the prefixes on their file-local `Meta`, `PluginDef` and `Internal` declarations. The gate's own rules are driven by `scripts/step-completeness.test.ts` over a synthetic repository, and an adversarial review of the first version closed four ways past them, each now with a test named after it: a `<name>.types.test.ts` holding only runtime `expect` calls (the exception needs a type-level assertion to earn the name), a one-line `lazy-output.ts` re-admitting the suite beside it (a helper module must be one `<name>.ts` reaches), a `namespace` without `declare` smuggling a `const` above `PluginDef` (only erased syntax may precede it, rather than a list of value kinds that a bare expression statement, a top-level `await` and `import x = require(…)` also walked past), and `map.async.test.ts` moved one directory up (a cross-step test's family must not be a step, since every all-lowercase step name is also a valid kebab-case family). What stays undecidable is stated as such: which section a local *type* belongs to, whether a helper is used rather than merely imported, and whether any assertion says something true.
- Cross-step tests — a contract spanning a family of steps and belonging to no one of them — are named `<family>.<aspect>.test.ts` at the steps root, so a test of a single step cannot sit among them looking like a family contract. `structural-failure-semantics`, `structural-issue-collection` and `structural-sync-fast-path` were renamed to that form, and `callbackErrorSentinel.ts` to `callback-error-sentinel.ts` to match the kebab-case rule a shared module already followed inside a step directory.
- `scripts/generate-bench-files.ts` is deleted. No `package.json` script referenced it, its heuristic output did not match what a step's benchmark has to be, and `scripts/step-completeness.ts` pointed a failing step at it as a starting point — which would have produced a file the same gate then rejected.
- Every built-in step now owns its documentation. `packages/internal/src/steps/<name>/<name>.doc.md` is the step's entry in the API reference — description, at least one example, and the issue codes it owns — and `docs/api/{overview,primitives,formats,structures,transforms,helpers}.md` is generated from those 114 entries plus six page templates under `scripts/docs-api-templates/`, which hold the prose that belongs to no single step: the import strategies, the naming convention, how issues are collected across the structural steps, the optional-field shorthand, the message-priority chain, the execution result. `pnpm docs:api` fails when a committed page stops matching its sources and `pnpm docs:api:update` rewrites them, the same pair as `pnpm api:surface`, and every generated page carries a banner saying so. What this removes is a second hand-maintained copy of the steps: 1,629 lines of prose whose only link back to an implementation was that a name happened to be spelled on both sides, where adding a step meant editing the step and then editing a page. The reference is now 3,388 lines, because a step that used to have a one-line bullet in a list now has an entry of its own.
- A step declares which page it belongs on and which section of it, in a `<!-- step-doc -->` block, and neither is inferred from its name — inferring `isXxx → formats` would file `isInteger` under string formats and would invent a category for a step nobody has written yet. Anything unplaceable fails rather than quietly leaving the step off the site: a step with no `.doc.md`, an unknown category, a section no template offers, a section slot no step fills, a page under `docs/api` that no entry in `apiPages` claims, a category page offering no section at all, and — because both are page-level id collisions that VitePress reports without naming a cause — a heading whose anchor is a step's anchor, or one section title used on two pages. Nothing is hand-ordered: pages come from one declaration, sections from the order their slots appear in the template, and entries within a section from a code-point sort of the public name, so check mode is stable. `scripts/docs-api.ts` is a pure function of an injected source tree, driven by 34 tests over a synthetic repository.
- `scripts/check-step-completeness.ts` reads a step's own `<name>.doc.md` instead of scanning `docs/api` for its name, which is a strictly stronger rule than the two it replaces. Those asked that *some* code span *somewhere* under `docs/api` wrote the name in call form, on the catalog page and on one further page, and that each issue code appeared somewhere on any of them — satisfiable by a page describing a different step, and satisfied for a step whose own section had been deleted as long as another entry mentioned it in passing. The entry now has to exist, in the step's own directory, holding its own name in call form, a description, a `ts` example, and every code it owns in a code span. `<name>.doc.md` joined the step unit's file set, so a Markdown file under any other name in a step directory is still rejected. What stays undecidable is unchanged and still stated in the failure text: whether the description is true, and whether the sentence beside a code is what that issue means.
- A `ts` example in a `.doc.md` reaches its page verbatim, `<!-- typecheck-… -->` directives included, and `pnpm docs:examples` compiles the generated pages against the built declarations as before. Since check mode makes the committed pages byte-identical to what the sources compose, a broken example fails one gate or the other and cannot reach the site: either the pages were regenerated and `docs:examples` compiles the broken example, or they were not and `docs:api` reports the difference. The API Reference sidebar in `docs/.vitepress/config.ts` is generated too, spliced between two region markers, so a page cannot be added on one side only.
- The Performance Impact gate decides what a changed file *means* rather than whether its bytes moved. `scripts/inert-change.ts` compares the two revisions of each changed path — a parsed YAML document deep-compared, or a TypeScript file reprinted from the compiler's AST with the comments no tool reads blanked out — and the selector ignores a path whose revisions come out equal, so a comment-only edit to a gate-defining file no longer forces the 55-minute complete comparison and a JSDoc correction to a step no longer selects that step's scenarios. This pull request's own gate paid the full run for three comment lines. Bundler annotations are not comments by that definition: `@__NO_SIDE_EFFECTS__` and `@__PURE__` change which code the bundle holds, so adding, removing, or moving one still selects. A `@ts-expect-error`, an `eslint-disable`, and a `v8 ignore` are, because none of them changes the emitted JavaScript and each is enforced by a gate that fails on its own. A path with no canonical form — JSON, a manifest, a lockfile's own format — and a file the diff added or deleted are never inert, so every conservative rule about one is unchanged. Replaying the twelve merges the selection was originally measured against, no merge that forced a complete comparison stopped forcing one.

- The Performance Impact gate measures each step's own benchmark cells instead of the cross-library scenarios. A step's `<name>.bench.ts` now declares its cells as data through `stepBench()`, and one declaration serves two drivers: `vitest bench` registers them for `pnpm bench`, and the gate imports the same file in a plain Node process whose `vitest` resolves to a shim and whose `'../..'` resolves to the dist build under test, reading the cells from a registry. So what the gate measures is what `pnpm bench` runs, cell for cell, and there is no second copy to drift. The scenarios are not deleted: they remain the unit of Performance Comparison and of `pnpm bench:coverage`, because a competitor spelling of the same work cannot live inside a step's own bench file.
- The cells were rebuilt rather than renamed, because an audit of all 341 found most of them measuring something other than the step they were named after. 341 became 245. Eight steps' failure cells never reached their own step — `toString`, `toLowercase`, `toUppercase`, `toTrimmed{,Start,End}`, `transform`, `toLength`, `toSliced`, and `toSorted` all failed inside `string`, `number`, or `array`; `object`, `strictObject`, and `looseObject` benched an empty shape whose child-execute loop never iterates; `array` benched `v.array(v.any())`, where no element can fail; `strictObject`'s "valid input - large" produced `unexpected_keys`, a failure recorded as a success; `bigint` and `symbol` had no success cell at all; `literal` wrapped two 1,000-character allocations around one comparison; 31 steps constructed the schema inside the timed region; and `toSize`, `toKeys`, `toValues`, `toEntries`, and `toArray` were 90% or more enclosing-structure work, so one `map` or `set` regression fired four false alarms elsewhere. Nine JavaScript baselines, the byte-identical duplicates, and the size and option-value variants are gone. Every cell is batched so one measured unit is roughly 1–10 µs, because `measure.mjs` reads the clock every 16 iterations at about 15 ns a read, which on a 2.6 ns cell is 88% of the measurement and turns a real 25% regression into 5%.
- What the cells now cover that nothing covered before: the dual traversal policy of the nine structures (9 `collectAllIssues` cells, previously 0 anywhere in the benchmark tree), the asynchronous path (12 cells against 1), the deferred message chain (2 designated cells; no cell anywhere passed a `message`, so `hasIssueDraft()` was always false and eight functions behind it never ran), `fallback`'s recovery decision, and the distinct algorithms behind an option rather than each option's values — `isEmoji({ registered })`, `isIp({ version })`, `toString({ radix })`, `toSplit(RegExp)`, `toSorted({ compareFn })`, `record`'s finite key domain, `tuple`'s rest region, and the array/Set dispatch in `toMapped`, `toFiltered`, and `isIncluding`.
- `pnpm bench:cells` (`scripts/check-bench-cells.ts`, in `pnpm verify`) makes that contract enforceable by driving the cells rather than reading them, the same idea as `benchmarks/src/step-audit.mjs` one level down. It executes every cell once outside any timed region and fails when a cell does not produce what it declares — issue codes included, which is what separates a cell measuring its own step from one that fails earlier in the chain — when a step has no cell that succeeds (one allowlisted exception, `never`, with its reason), when a step owning an issue code has no cell producing one of its own, when construction sits inside a timed region (decided from the AST: a `run` is exactly one call on a reference built above the cells), when a bench file imports anything but the package entry and the declaration helper, and when a measured unit is more than two orders of magnitude from the target. Each message says what its rule cannot decide; none of them can decide whether a cell measures work worth measuring, which is why the cell set is small enough to read.
- The impact selection's second half changed from `steps → scenarios whose declared steps name them` to `steps → the step's own cells`, which removes the last hand-maintained declaration deciding what the gate measures: a cell's step is the directory it lives in. The first half is untouched. `*.bench.ts` gained a third classification — it cannot change either build but it declares the measurement, so it selects its own step's cells rather than nothing or everything — and `scripts/check-impact-triggers.ts` gained the matching rule, since a rewritten cell that never starts the workflow is a measurement change nothing looks at. The canary is now the construction and cold cells plus thirteen named core cells.
- A row is classified by its 95% interval instead of its point estimate: `cleared` when the whole interval is inside ±5%, `regression` when it is entirely at or below −5%, `severe` when it is a regression and the point estimate is at or below −10%, and `inconclusive` when it spans a threshold. `inconclusive` is not a pass — it gets its own verdict and its rows are named — and it does not fail the job on its own. This fixes errors measured in both directions on hosted runners: a `before == after` null run called `construct/tuple` a regression at −5.32% with a 3.12% paired RME, precise by the old rule and false by construction, while a row at −12% with 6% RME was discarded for imprecision and passed in silence. `stabilityThreshold` is now a reported diagnostic and decides nothing; the group aggregate runs over decisive rows, improvements included. Repetitions stay at five and no threshold moved.
- `scripts/check-impact-triggers.ts` also checks that the impact gate's measurement loop still counterbalances the two sides by repetition parity. Pairing cancels machine speed, which is what makes a paired ratio comparable across runners, but not monotonic drift — temperature, allocator and GC state, background load — and a loop that always measured the baseline first would put every repetition's drift on the candidate. The alternation survived the rewrite into four shard jobs; the rule costs less than noticing that it did not survive the next one, and it lives in the check that already reads the workflow because the property is shell rather than a module a test can reach.
- The group verdict is its own estimator instead of a summary of the rows that decided. Per repetition the log ratios of every cell selected into a group are averaged into `G_r`, and the group is judged by the Student-t interval across `G_1 … G_5`: severe when that whole interval is at or below −5%, converted back with `exp` like a row. The aggregate was a geometric mean over the group's *decisive* rows, which conditions the estimate on the measurement outcome — a row survives that filter when its own effect is large or its own noise is low, so the mean ran over exactly the rows most likely to trigger it. `exp(mean(G))` is still the geometric mean of every cell's ratio, so the aggregate did not change shape; what it gained is an interval, and averaging within a repetition before taking the spread across repetitions is what earns it. Two consequences are now tested: an inconclusive row's cell stays in its group's estimate and widens the interval instead of being dropped, and a group can be decisive where none of its rows is. The trigger's prerequisite changes from two decisive rows to two **measured** rows — a property of the selection, decided before anything is measured — and `minimumDecisiveScenariosPerGroup` in `impact.json` is renamed `minimumScenariosPerGroup`. Group rows carry their own interval and verdict, and the scoped-coverage reporting is unchanged: `measured/total` per group, and the statement that a scoped aggregate is not comparable with an unscoped one.
- The paired comparison uses one estimator instead of two. Each repetition contributes `d_r = ln(candidate_r / baseline_r)`, the estimate is `mean(d)` with a 95% Student-t interval, and both are converted back with `exp`, so the reported change `exp(mean(d)) − 1` and the interval are the same statistic. Before, the interval was centred on the mean of the paired ratios while the reported and severe-triggering point estimate was their median: two estimands that can disagree about a row, with the deciding one not the one on display. The log form also makes improvement and regression multiplicatively symmetric — a doubling and a halving are `±ln 2` rather than `+1.0` and `−0.5` — which is what lets a group aggregate be a mean of the same numbers. Student's t stays, and no threshold moved. `pairedRme` is now that half-width in percent, which agrees with the relative margin of error of the ratios to first order: the null run's `construct/tuple` cell reads 3.12% under both. `statistics.mjs` gained `confidenceHalfWidth` as the primitive and `pairedLogRatioEstimate` as the estimator, keeping one definition of measurement uncertainty for the runner and the comparison.
- The comparison and reporting stage no longer loads the code under test. Coverage denominators used to be built by collecting the cells, which imports every `<name>.bench.ts` under a loader that resolves the library to a built dist, so the first sharded run measured all 245 cells across four shards and then failed in `compare` with `VALCHECKER_DIST_URL is not set`. Setting the variable there was the wrong fix: `pnpm --dir benchmarks cells --catalog-output <path>` now persists the cell catalog as data while it measures, `compare --cell-catalog <path>` reads that file, and the compare job runs with `build: 'false'` so the coupling cannot return quietly. The catalog carries a hash of the cell set; each shard records the hash it measured against, and `merge`, the measurement identity in `comparability.mjs`, and `compare` each refuse a mismatch, because a stale catalog would misstate every group's coverage without changing a number. A cell run's `scenarioCatalog` now lists the cells its shard was *assigned* rather than only the ones it could measure, which is what the cross-library runner already recorded and what keeps `p % count` invertible when a cell cannot execute against one of the two builds.
- Every comparison prints `measured N / added M / removed K` whether or not any of them is zero. `added` cells execute against the candidate build and not the baseline's — a new step's cells — and `removed` cells the other way round, which is a cell whose subject stopped working; both are named, not counted. This also removes a hard failure: an asymmetric cell set used to abort the comparison with `Candidate contains scenarios absent from baseline`, so a pull request that added a step could not be measured at all. What the counts cannot see is stated in the report: a cell deleted from the candidate tree is not in the catalog either, because the cells are the apparatus and come from the checked-out ref.
- The gate shards four ways and merges before the verdict, so the group aggregate is computed once over the complete cell set. The previous "deliberately NOT sharded" rationale is replaced with the measurements that refute it: 55m12s of measurement against about 40s of non-shardable checkout, setup, both builds, and scoping, so wall time is 40s + measurement/N and four shards is about 28.5 minutes.

### Added

- `isEmoji({ registered: true })` opts in to Unicode's RGI set, the sequences vendors are expected to render. It compiles `\p{RGI_Emoji}` through `new RegExp` inside a capability probe rather than a regular-expression literal, and where the runtime has no `v` flag it fails with the new operation issue `isEmoji:unsupported_registered_set` (payload `{ value, error }`) instead of falling back. The probe runs at most once, on the first `{ registered: true }` schema built, rather than at module load: Rollup's default `tryCatchDeoptimization: true` abandons analysis of a `try` block, so a module-scope probe survived tree-shaking and cost an entry importing only `string` and `isEmail` 132 B and one `new RegExp(…, 'gv')` at import. There is deliberately no fallback: an accepted set that depends on the runtime is a wrong answer that is harder to notice than a failure, which is the whole reason the option exists.

### Fixed

- `tuple()` reads the input's `length` once, so a child that mutates the array it is being validated against can no longer move the rest slice or the suffix indices mid-traversal. The synchronous entry point read `length` and the asynchronous continuation re-read `value.length`, which is the same divergence fixed in `array()` above.
- `map()` and `set()` report `firstIndex` correctly when `collectAllIssues` collects past a failed entry. A buffered entry was recorded under its buffer position, which equals its source index only until something is skipped; the buffer is now materialized while the two still agree.
- `isEmoji()` no longer accepts a lone `Emoji_Component` on either accepted set. `\p{RGI_Emoji}` matches the five skin-tone modifiers (`🏻`–`🏿`) and the four hair components (`🦰`–`🦳`) as single characters, so the previous implementation accepted `🏽` as an emoji, and accepted `👪🏻` and `👍🏽🏽` by decomposing them into a registered emoji plus a bare component. The registered path now matches `[\p{RGI_Emoji}--\p{Emoji_Component}]`. A component is still accepted where the grammar gives it a position: `👨‍🦰` and `👍🏽` are unaffected. Verified by enumerating the registered set out of the `v`-flag sub-properties — 3,953 engine-confirmed members across `Basic_Emoji`, `Emoji_Keycap_Sequence`, `RGI_Emoji_Modifier_Sequence`, `RGI_Emoji_Flag_Sequence`, `RGI_Emoji_Tag_Sequence`, and `RGI_Emoji_ZWJ_Sequence`, of which 259 of the 676 regional-indicator pairs are members — where the nine lone components are the only members either path now rejects.
- Importing `valchecker` no longer requires the regular-expression `v` flag. `isEmoji`'s pattern was a literal carrying the flag, and an unsupported flag in a literal is a parse-time `SyntaxError`, so on an engine without `v` the whole module failed to load and took every other step with it — a Safari 16 user could not import the package at all, not just `isEmoji`. The default accepted set now needs only the `u` flag and the `v` flag lives behind a constructor.

- `scripts/check-step-completeness.ts` (`pnpm steps:complete`, run by `pnpm verify` through `test:quality`) fails a built-in step that is missing a colocated `<name>.test.ts` registering at least one `it` or `test`, a `<name>.bench.ts` declaring cells with `stepBench` (the rule was `calls bench` until the cell format replaced it), a runtime export in `api-surface.json`, a `<name>.doc.md` whose `### ` entry writes its name in call form in a code span, describes it, and holds a `ts` example, or an owned issue code appearing in a code span of that entry and in a string in one of the directory's tests. Fenced code blocks and HTML comments are removed from Markdown before matching, and TypeScript strings are read from the parsed AST, so a mention inside an HTML comment or a `//` comment satisfies nothing. It reports every missing piece for every incomplete step in one message. Coverage is an unreliable substitute for the test rule: other steps' tests execute a step's implementation, and deleting the tests of nine steps at once, the per-file policy caught five and let four through.
- `scripts/step-completeness.ts` and `scripts/step-inventory.ts` hold that gate's logic as pure functions of an injected source tree, covered by 65 tests (51 and 14). Each rule that can be satisfied without the requirement being met — a test case asserting nothing, an issue code in a comment, a step named in a sentence saying it does not exist — has a test pinning either the rejection or the admitted limit.

### Fixed

- The API reference documents the issue codes `looseObject:expected_object`, `looseObject:missing_key`, and `fallback:failed`, which no page under `docs/api` had listed.
- `scripts/check-issue-codes.ts`, `scripts/check-step-completeness.ts`, and `scripts/check-benchmark-coverage.ts` fail on a step directory they cannot read as a step, instead of skipping it and reporting a count over whatever they happened to find. The discovered set is cross-checked against the re-exports in `packages/internal/src/steps/index.ts`, so the two disagreeing is a failure rather than a silently smaller scan.
- Two default messages now end with a full stop, which every other message in the library already did: `check:failed`'s `'Check failed'` became `'Check failed.'`, and `core:unknown_exception`'s `'An unexpected error occurred during step execution'` became `'An unexpected error occurred during step execution.'`. These were the only two, found by sweeping every `defaultMessage` under `steps/` and in the core; `check`'s sibling `check:callback_failed` and the core's sibling `core:message_exception` were both already punctuated. This is user-visible output, so a test asserting either string exactly needs the stop added.
- `record()`'s IDE contract said `'record:expected_object'` fires when the value "is not a plain object". Its guard is `typeof value !== 'object' || value == null || Array.isArray(value)`, which admits a `Date`, a `Map`, and any class instance, so it is not a plain-object test. The API reference entry had already been corrected; the JSDoc now agrees with it and with the other object steps.
- `union()`'s entry said that importing a shorthand provider without registering it "does not enable its shorthand", which reads as a silently unavailable branch. It throws a `TypeError` naming the branch index while the schema is being constructed, as do an empty branch array and a hole in a sparse one. `variant()`'s five construction guards and `record()`'s key-schema guard were likewise undocumented, though all of them are tested; every step that throws at construction now says so, as `tuple`, `isMimeType`, `isMultipleOf`, `isOneOf`, `isMatching`, `toNormalized`, `toMappedBoolean` and `templateLiteral` already did.
- `tuple()`'s entry now documents the one guard that fires during execution rather than construction: a rest schema succeeding with a non-array. It does not escape the result type — the `TypeError` is caught and reported as the fatal internal issue `core:unknown_exception` with `payload.method` `'tuple'` — and it now has a test pinning that, which it did not before.
- `array()` reads the input's `length` once, so how many indexes it validates no longer depends on whether a child schema happens to be asynchronous. The synchronous path always snapshotted the length (`const len = value.length`, then `new Array(len)`), but the asynchronous continuation re-read `value.length` on every iteration, so an element schema that appended to the array it was validating extended its own traversal: `v.array(item).execute([1, 2])` with an `async` child pushing five entries returned seven outputs against the two the same schema returns synchronously, and wrote them past the end of an output allocated for two. Only a child that mutates the input array it is being validated against could observe this, and no documented behaviour changes — `array`'s entry already said every index up to the array's `length` is validated, and the corrected asynchronous path is what the synchronous path always did — so there is nothing to migrate.
- `pnpm docs:api` no longer reports all seven generated files as stale on a Windows checkout. The composition splits every source on `/\r?\n/` and joins with `\n`, so what it composes is canonically LF, but the committed pages were compared as the bytes git left in the working tree — CRLF on `windows-latest`, where both Node versions failed the gate while ubuntu and macOS passed. The comparison normalizes line endings and now lives in `scripts/docs-api.ts` beside the composition, so a test over a synthetic tree drives it rather than only the CLI; the whole file is still compared, so a one-character hand-edit still names the file.

## [0.0.33] - 2026-07-27

The first release in six months, published to the npm `latest` tag. It carries everything prepared for the `1.0.0-rc.0` candidate together with the refinements made on top of it; the 1.0 line has not shipped, so this continues the 0.x series, where a breaking change may land in any release.

Read the breaking entries below before upgrading. A dependency written as `^0.0.32` does not resolve to this release, but `~0.0.32` does, as does any range looser than a caret — and a fresh `npm install valchecker` now gets it. Pin the exact version if you are not ready.

### Added

- Plugin capabilities: `implStepPlugin(impl, operationMode, capabilities)` takes a symbol-keyed record of runtime capabilities, and a step implementation reads every registered entry through `context.getCapabilities(capability)` in registration order. This is how one step discovers what another registered step can do without importing it or hardcoding its name; keys are well-known symbols, mirroring the construction metadata channel. A plugin def declares the matching type-state under a reserved `Capabilities` slot. Capabilities must be declared inside the `implStepPlugin` call, because a separate top-level declaration is eliminated as an unused side effect by the bundler.
- `union` resolves shorthand branches through the registered `unionShorthandCapability` providers instead of a hardcoded list, so a third-party plugin can add a shorthand branch kind. A provider declares which values it claims, the initial step that validates them, and the parameters to pass; providers are consulted in registration order and the first match wins.
- Date steps: `date()` (initial schema accepting a `Date` and rejecting an Invalid Date, owning `date:expected_date` and `date:invalid_date`), `isAfter(bound)` / `isBefore(bound)` (strict `getTime()` comparison, owning `isAfter:expected_after` / `isBefore:expected_before`), and `toDate()` (converts a `string | number` to a `Date`, owning `toDate:conversion_failed`).
- `file()` and `blob()` initial schemas validate `File` and `Blob` values with feature-detected globals, preserving the value and inferring the matching output type. They own `file:expected_file` and `blob:expected_blob`.
- `isMimeType(types, options?)` validates a value's `type` string against one or a list of MIME types with case-insensitive `image/*`-style wildcards, preserving the value. It owns `isMimeType:unexpected_mime_type` with payload `{ value, expected, actual }` and applies to any output with a `type` string, including `File` and `Blob`. Size validation reuses the existing `isSizeAtLeast`/`isSizeAtMost`/`isSizeExactly` steps.
- String-format validators: `isEmail`, `isUrl(options?)` (WHATWG `URL` parse with a case-insensitive scheme allow-list, default `['http', 'https']`), `isUuid`, `isNanoid`, `isCuid2`, `isUlid`, `isBase64`, `isBase64Url`, `isHex`, `isJwt`, `isIp(options?)` (optional `version` `4`/`6`), `isHostname`, `isMac`, `isEmoji`, `isIsoDate`, `isIsoTime`, and `isIsoDateTime`. Each validates its named string format and preserves the value, owning a single `<step>:expected_<format>` issue (for example `isEmail:expected_email`, `isUuid:expected_uuid`, `isIp:expected_ip`).
- `record({ key, value, message?, collectAllIssues? })` initial schema validates and transforms every own enumerable entry of a plain object, aligning with TypeScript's `Record<K, V>`. A wide key domain (`string`/`number`/`symbol`/template) produces an open index signature and validates every key with transformed-key uniqueness (`record:duplicate_transformed_key`); a finite key domain (a `literal`, a union of literals, or `isOneOf`) produces an all-required, exhaustive object with `record:missing_key` and `record:unexpected_keys`, never executing the key schema. Also owns `record:expected_object`.
- `tuple(elements, options?)` initial schema validates a fixed-shape array positionally, aligning with a TypeScript tuple. A single `'...'` marker declares the next entry as a rest region whose array output is spread (`v.tuple([v.string(), '...', v.array(v.number())])` → `[string, ...number[]]`); leading, middle, and trailing rest are supported. Owns `tuple:expected_array`, `tuple:unexpected_length`, and `tuple:expected_length_at_least`. The object optional-field `[schema]` shorthand is unchanged and does not collide.
- `literal`, `isOneOf`, and `union` (of literal branches) now advertise their finite accepted/output value set through the construction-time metadata channel under a well-known symbol (frozen, dropped by any further chaining), which is what lets `record` drive an exhaustive finite key domain. A new `utils.replaceIssuePath` rewrites a child issue's path outright (used by `tuple`'s rest-region index remapping).
- `templateLiteral(parts)` initial schema: validates a string against an assembled TypeScript template-literal type and infers that exact output type, with cross-product union expansion. Parts are interpolatable literals or bare initial schemas (`string`, `number`, `bigint`, `boolean`, `literal`, `null`, `undefined`, `union`, nested `templateLiteral`). Matching and inference mirror the TypeScript checker's placeholder split rule (leftmost, one-character adjacent-placeholder capture, no backtracking, all-string reduction), not a regular expression. Owns `templateLiteral:expected_template_literal` (payload `{ value, template }`).
- `@valchecker/internal` exports `runtimeExecutionStepDefMarker` (also re-exported from the public `valchecker` package), the shared step-plugin discovery symbol previously duplicated as a `Symbol.for()` string in `@valchecker/all-steps`.
- Construction-time schema-metadata channel: a step implementation can call `utils.setMetadata(key, value)` to attach a symbol-keyed entry to the schema being built, surfaced on `~core.metadata` (`Readonly<Record<symbol, unknown>> | undefined`) and read back by well-known symbol. Metadata describes only the final step and is dropped on chaining. A typed `TExecutionContext.literalMembers` field mirrors the finite literal-member set at the type level with drop-by-default propagation. Both are inert until a step declares them.
- Direct discriminated-union dispatch through `variant({ discriminator, variants, message? })`, with own-property selection, selected-branch issue context, and precise sync/maybe-async inference.
- Collection callback transforms: Set `toMapped()`/`toFiltered()` and Map `toMappedKeys()`/`toMappedValues()` with step-start snapshots, typed operation issues, and explicit SameValueZero collision diagnostics.
- Explicit collection representation transforms: Set `toArray()` and Map `toKeys()`, `toValues()`, and `toEntries()`.
- Map and Set size/membership steps: size-aware `isEmpty()`/`isNotEmpty()`, `isSizeAtLeast()`, `isSizeAtMost()`, `isSizeExactly()`, `toSize()`, Set `isIncluding()`, and Map `isIncludingKey()`/`isIncludingValue()`.
- `map()` and `set()` initial schemas with insertion-ordered child validation and transformation, stable collection paths, sync/maybe-async preservation, and explicit transformed-key/item collision diagnostics.
- Exact length, string/array inclusion, regular-expression, strict numeric-bound, divisibility, and safe-integer validation steps.
- Primitive equality and tuple membership through `isEqualTo()` and `isOneOf()` with `Object.is` semantics and state-aware output narrowing.
- Defined, non-null, and non-nullish narrowing steps that disappear once their excluded values are impossible.
- Unicode string normalization through `toNormalized()`.
- Array mapping through `toMapped()` with typed output and structured callback-operation diagnostics.
- Standard Schema V1 support on every schema through `~standard`.
- Native `PromiseLike` assimilation for callback-driven validation and transformation steps.
- `.toAsync()` for callers that require every execution to return a native promise.
- First-success transformed-output semantics for `union()`.
- Graph-aware `intersection()` composition for compatible plain objects, cycles, aliases, enumerable symbol keys, and same-reference non-plain values.
- Safe own-property handling for declared `__proto__` fields.

### Changed

- The `${number}` and `${bigint}` template-literal grammars have one definition each, owned by `looseNumber` and `looseBigint` and shared with `templateLiteral`'s placeholders, replacing a regex that was duplicated verbatim between `looseBigint.ts` and `template-literal-part.ts` and two spellings of the same number rule. Both cited tsc's `isValidBigIntString`/`isValidNumberString`, so they were one rule written twice. No behaviour changes; a test guards against the duplication returning.
- **Breaking:** `isLengthAtLeast` issue payloads use `minimumLength` instead of `minimum`, and `isLengthAtMost` uses `maximumLength` instead of `maximum`, distinguishing length bounds from the unqualified `minimum`/`maximum` of numeric-value bounds. Method parameter names are unchanged.
- **Breaking:** `isIncluding` reports the searched value under a single `expected` payload key across its string, array, and Set variants; the string variant previously used `search`. Method parameter names are unchanged.
- **Breaking:** `toNumber:conversion_failed` and `toBigint:conversion_failed` are now `operation` issues instead of `validation`, aligning with the rule that a throwing native conversion is an operation failure while static or parse invalidity remains a validation failure.
- **Breaking:** `toJSONString` now fails on sparse array holes with `toJSONString:unserializable` (`{ reason: 'undefined_result' }`) at the hole's path instead of serializing them to `null`, matching its existing strictness for explicit `undefined`, function, and symbol values.
- **Breaking:** `toString` takes a single trailing options object `{ radix?, message? }` instead of native positional arguments (`toString(16)` becomes `toString({ radix: 16 })`) and now supports a custom failure `message`. It continues to delegate to the value's own `toString` instance method.
- The advanced `~core` runtime object no longer allocates the dead `executionStepContext` and `registeredExecutionStepPlugins` slots. The corresponding `TValchecker['~core']` interface properties are now type-level phantoms with no runtime backing; reading them yields `undefined`.
- `StepPluginImpl` now derives the impl-side `utils` output type by reading `InferOutput` off the method's actual `Valchecker` return instead of pattern-matching `Next<{ output: infer O }>`. This is behavior-preserving for every valid plugin (whose method always returns a `Use<Valchecker>`) and only affects third-party plugin authors' impl-side inference; it fixes output extraction collapsing when the returned context carries an unnamed non-`undefined` field such as `literalMembers`.
- **Breaking (edge):** `map()` and `set()` now iterate the input lazily from the native `Map`/`Set` iterator instead of snapshotting all entries at execution start. Two edge behaviors change: iteration ignores an overridden instance `forEach`/`entries`/`values` (validation always sees the collection's real contents), and there is no longer a mutation-isolation guarantee — a child step that mutates the input during validation observes live iteration, matching valibot/zod. Insertion order, transformed-key/item collision detection, `collectAllIssues`, and sync/maybe-async behavior are unchanged.
- `array()`, `set()`, `map()`, `object()`, `strictObject()`, `looseObject()`, and `intersection()` now stop after the first recoverable structural or child failure by default; pass `collectAllIssues: true` to preserve complete recoverable issue collection. Default asynchronous intersections now avoid starting later branches after an earlier failure.
- Standardized all message-bearing built-in step parameters around trailing options objects and removed positional messages.
- Number `isMultipleOf()` accepts ordinary decimal multiples using a documented floating-point tolerance, while bigint divisibility remains exact.
- The supported runtime is Node.js 22 or newer.
- Published packages are ESM-only. CommonJS consumers must use dynamic `import()`.
- `execute()` now has a documented sync/maybe-async contract instead of being described as universally asynchronous.
- Callback-driven steps may return direct values or thenables according to their step contract.
- `object()` omits unknown input properties from output, while `looseObject()` preserves them.
- `strictObject()` checks all enumerable own string and symbol keys.
- `use()` preserves delegated transformed output and issue types.
- `@valchecker/internal` is the semver-covered advanced root API for step-plugin authors; package-private source paths remain unsupported.
- Lint checks are non-mutating; automatic formatting is available through `pnpm lint:fix`.
- Version changes are reviewed pull requests. The release workflow no longer edits Git history or creates tags.
- Built-in step names now expose their pipeline role: initial schemas use nouns, built-in validations use `isXxx`, and concrete transformations use `toXxx`. Generic `check()` and `transform()` retain their direct names.
- `number()` now matches the TypeScript `number` primitive and accepts `NaN`, `Infinity`, and `-Infinity`; finite-number policy is explicit through `isFinite()`.
- `looseNumber()` now accepts `number` or a TypeScript-compatible number string and normalizes output to `number`, rather than duplicating the old `number()` behavior.
- Numeric bounds and length bounds are separate steps so their intent and payloads are explicit.
- Primitive `toXxx()` conversions follow JavaScript `Number()`, `Boolean()`, and `BigInt()` semantics without hidden finite, parsing, truthiness, or precision-safety policies.
- Identity primitive conversions are excluded from state-aware autocomplete; policy-bearing conversions use explicit names.
- Failure issue arrays are typed as non-empty tuples.
- `core:unknown_exception` now exposes the received execution result as `receivedResult` instead of the misleading `value` field.
- Message maps preserve same-code payload variants and allow callbacks to return `null` or `undefined` to continue resolution.
- Combinators now treat internal issues as fatal: union cannot skip them, fallback cannot recover them, and object/array sibling traversal stops immediately.
- `intersection:conflicting_outputs` reports precise conflict paths, branch indices, values, and reason codes.
- Fallback callback failures retain the original received issues and append an `operation`-category `fallback:failed` issue with a required error.
- `check:failed` now discriminates returned-false and returned-message payloads; callback exceptions use `check:callback_failed`.
- `transform`, `toFiltered`, and `toSorted` callback exceptions now preserve phase or operand context in operation issues.
- `toJSONString()` reports stable reason/path payloads, performs a single-read preflight, preserves boxed primitive semantics, and classifies getter, Proxy, and `toJSON` failures as operations.
- Length validation issues include the observed `length`; mapped-boolean failures include immutable mapping snapshots.
- `literal()` uses `Object.is`, and bigint conversion failures use `toBigint:conversion_failed`.

### Performance

- `isIp()` validates IPv4 octet ranges in its pattern instead of splitting the address and comparing parsed numbers. Measured: a valid address 101.4 ns to 25.8 ns (3.93x), an out-of-range octet 3.47x, a malformed string 2.31x. The accepted set is unchanged across 4,130 generated inputs covering every value `0`-`999` in each of the four positions, 29 octet spellings, and malformed shapes. IPv6 keeps its procedural path, and inherits the improvement for its embedded-IPv4 tail.
- `isIsoTime()` validates field ranges as part of its pattern instead of comparing parsed numbers after a shape match, and the time grammar now has one definition shared with `isIsoDateTime()`'s time and offset halves. Measured end to end through `execute()`, both versions registered in one process and interleaved: a valid time 103.9 ns to 33.0 ns (3.15x), a fractional time 127.2 ns to 35.3 ns (3.61x), an out-of-range field 89.0 ns to 35.7 ns (2.50x), a malformed string 39.8 ns to 35.7 ns (1.11x). Every path improves, and unlike the calendar change above there is no shape that costs more: a time has no branch as expensive as the leap-day alternation to walk before failing. `isIsoDateTime`'s composed pattern source is byte-identical to before, and `isIsoTime`'s accepted set is unchanged across an exhaustive run of all 1,000,000 `HH:MM:SS` field combinations plus fractional and malformed shapes.
- `isIsoDate()` and `isIsoDateTime()` validate the calendar with a single pattern instead of round-tripping through `Date`. Month lengths and the leap-year rule are encoded in the shared date source, so a success no longer allocates a `Date` or parses the date and time fields as numbers. Validating a date-time measured 298 ns before and 36 ns after (2026-07-27); `string-format/iso-date-time-valid` was the largest gap in the cross-library suite, 3.89x behind the fastest peer in the full profile run on `ubuntu-24.04` ([30227011273](https://github.com/DevilTea/valchecker/actions/runs/30227011273)). Failure paths improve too — an impossible date is 6.6x faster and a malformed string 1.5x faster — with one exception: a near miss whose date part is valid, such as `2026-07-23 12:30:00`, costs about 11% more, because the calendar alternation now runs before the mismatch is found. The accepted set is unchanged, including the pre-existing rejection of `0000-02-29`: the two implementations agree on 25,512 generated inputs covering every day of every month across leap years, leap centuries and the `0000`-`0099` range, the hour, minute, second, offset and fractional-second boundaries, and malformed shapes.
- `intersection()` merges disjoint flat plain objects without allocating a property descriptor per key. The merge scans own enumerable properties with `Object.keys` plus the enumerable own symbols, reads each value once, and builds the output from those values. Measured with the standard profile over three interleaved pairs: `intersection/valid` improves about +26% in throughput (roughly 450-460 ns to 350-367 ns, depending on which scenarios share the worker process), `cold/intersection-valid` about +11%, construction unchanged, and the collection and primitive scenarios unaffected within run-to-run noise. The accessor-snapshot contract holds on both paths: the shallow merge assigns the values it read rather than re-reading them, and when it declines it hands them to the general graph merge.
- Schema instances dispatch through a shared prototype instead of a per-instance `Proxy` `get` trap. This removes a fixed per-property-read cost paid on every `execute`, `~execute`, and `~core` access (including the internal per-child reads structural steps perform), with no change to the public property surface.
- `map()` / `set()` first-issue short-circuit no longer scans the whole collection (lazy native iteration).

### Fixed

- **Breaking (edge):** `isJwt()` now applies the base64url length rule to its segments, not just their alphabet. A base64url string never has a length of `1 (mod 4)`, because a final group of one character cannot encode a byte, so tokens with such a payload or signature are now rejected; `isBase64Url()` already rejected those strings, and the two steps disagreed. A header of that length was already rejected, since it must base64-decode to JSON. Header and payload must still be non-empty and an empty signature is still accepted, both unchanged. The rule now has one definition shared by both steps, and costs 1-4% more than the alphabet-only check it replaces.
- **Breaking (edge):** a plugin def's type-state-only capabilities live under a `Capabilities` slot instead of at the top level, so they no longer appear in `RegisteredStepMethodName`. On any instance registering `literal`, `null_`, or `undefined_` — including the default `v` — the literal `'UnionShorthand'` was part of `core:unknown_exception`'s `payload.method` union, advertising a method that can never run. Third-party plugin defs that declared a top-level type-state field must move it under `Capabilities`.
- `union()` no longer accepts a shorthand branch at the type level that its runtime cannot resolve. Branch normalization went through a hardcoded `null`/`undefined`/literal chain while the accepted type was the union of every registered provider's declared input, so a third-party provider typechecked and then threw `Invalid union branch`. The rejection message now names the category rather than a specific missing step, since the registry cannot know which provider would have claimed the value.
- `union()`'s literal-shorthand branch resolution no longer widens the inferred output and issue types with every registered shorthand provider. A provider now contributes only when the branch satisfies its declared `input`, mirroring the runtime dispatch, so `v.union(['read', 'write'])` infers `'read' | 'write'` instead of `'read' | 'write' | null | undefined` on any instance registering `null_`/`undefined_` — including the default `v`. This also unblocks `record({ key: v.union(['read', 'write']), … })`, whose key domain the widened output made incoherent, and removes the spurious `` `${T}null` ``/`` `${T}undefined` `` members a `templateLiteral` part gained from a shorthand union (`v.templateLiteral([v.number(), v.union(['px', 'em'])])` inferred four members and now infers two). Runtime behaviour and `literalMembers` were already correct.
- `~standard.validate` now carries the schema output type per Standard Schema V1, improving assignability to `StandardSchemaV1<_, Output>` consumers.

### Security

- npm publication is restricted to a manually dispatched workflow on `main`, protected by the `npm` GitHub environment.
- Publication uses job-scoped OIDC and rejects `NPM_TOKEN` and `NODE_AUTH_TOKEN`.
- Exact tarball paths, sizes, SHA-256 checksums, package order, commit identity, npm tag, and typed confirmation are verified immediately before publication.
- CI rejects source files, tests, benchmarks, TypeScript configuration, and unresolved workspace/catalog dependency protocols in published tarballs.
